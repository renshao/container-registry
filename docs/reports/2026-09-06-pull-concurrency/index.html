Where does summ stop scaling?

Across 45,400 pulls at up to 400 simultaneous clients, on a single EC2 instance, it didn't. summ held the network's line rate flat from 25 concurrent pullers to 400 with zero failures, on under three-quarters of one CPU core. The ceiling this test found belongs to the NIC, not the registry.

01The finding

One VM, one registry process running at a time, same NVMe, same image list in the same order. Only concurrency changes.

summ v0.1.0-rc.1 reached 37.4 Gbps of measured egress — line rate for this instance class — at 25 concurrent pullers, and stayed there through 50, 100, 200 and 400. The curve is flat because there is nothing left to give: the network card is full.

distribution, the reference Go implementation, never reached line rate on the same box, and moved away from it as concurrency rose — from 3,985 MB/s at 25 clients down to 3,471 at 400. That is the shape of a server becoming the bottleneck. summ's flat line is the shape of one that hasn't.

02Throughput against the wall

Small-image corpus — six images averaging 13 MB, where a pull is mostly manifest fetch, blob open and connection setup rather than streaming.

03What a client waits

Median time to complete one whole image pull — manifest, config and every layer.

Throughput is the server's view. Latency is the puller's, and it is the number a CI job or a node starting 200 containers actually feels. summ's median pull is faster at every level, and the margin grows as the machine fills: 1.20× at 25 clients, 1.49× at 400.

04Where summ looks worse

One result did not go summ's way, and it is the one worth acting on.

Tail latency

summ's slowest pulls are proportionally slower than distribution's

Measured as the spread between a typical pull and a bad one — p99 divided by p50 — summ is the wider distribution above 50 concurrent clients. At 100 concurrent, summ's p99 is 4.75× its median (216 ms → 1,025 ms) while distribution's is 1.81× (331 ms → 599 ms). In absolute terms distribution's p99 is genuinely better at that one point: 599 ms against 1,025 ms.

A caveat that does not excuse it: summ is moving 23% more bytes per second at the same nominal concurrency, so it is under more real load. But the pattern holds across 100, 200 and 400, and a consistent 3–5× spread is a characteristic, not noise. If summ's tail matched its median, it would win every column on this page.

06What this does not establish

Read these before quoting any number above.

  • summ's actual ceiling is unknown. It saturated a 40 Gbps NIC at 0.72 of one core with seven cores idle. Finding where it breaks needs a faster network or several load generators, not a bigger sweep.
  • This is a warm-working-set test. The corpora are 7.3 GB and 78 MB against 32 GiB of RAM. Caches are dropped before every point, so each begins cold, but a long point ends up serving from page cache. It measures the request path, not the disk.
  • One run per point, no repeats. The harness supports --repeats for interleaved sweeps; this run used one pass. Differences under about 5% should not be read as real.
  • Single region, single instance family. ap-southeast-2, m6idn.2xlarge, Ubuntu 24.04, ext4 on local NVMe. Both engines ran natively under systemd — no containers on either side.
  • Pull only. Push throughput was measured incidentally during corpus setup and is not comparable across engines, because the first engine populated also absorbs the upstream fetch.

Harness: bench/concurrency.sh in summ-bench, driving a Rust OCI client that simulates containerd — GET manifest, then all blobs at fanout 3. Engine restarted and /proc/sys/vm/drop_caches flushed before every point; one engine running at a time; identical image list in identical order, verified servable by both engines before the sweep. Registry CPU and egress read from the host's own /proc and /sys counters, independently of the client's numbers.

Runs conc-20260906-092504 (mixed) and conc-20260906-093259 (small). Raw per-pull samples are in the run directories; concurrency.sh --summary-only <dir> re-renders from them. All AWS resources destroyed at completion.
